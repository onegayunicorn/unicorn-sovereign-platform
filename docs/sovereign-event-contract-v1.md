# Sovereign Ecosystem Event Contract v1

Status: PROPOSED CONTRACT — integration implementation and interoperability tests are pending.

This contract defines the shared read-only event shape used by Photonic Codex, Unicorn Sovereign Platform, and Quantum Multiversal Nexus. Each repository remains authoritative for its own state. Consumers must not upgrade another system's evidence classification or infer that a service is healthy from a stale or missing report.

## 1. Required event envelope

```json
{
  "schema_version": "1.0",
  "event_id": "UUID",
  "timestamp": "2026-10-11T00:00:00Z",
  "source": "unicorn-sovereign-platform",
  "type": "capability.report",
  "classification": "SIMULATED",
  "correlation_id": null,
  "provenance": {
    "repository": "onegayunicorn/unicorn-sovereign-platform",
    "revision": "git-commit-sha",
    "evidence_uri": null
  },
  "payload": {}
}
```

Required fields: `schema_version`, `event_id`, `timestamp`, `source`, `type`, `classification`, `payload`. The `provenance` object is required for capability and test-result claims. `correlation_id` may be null.

- `event_id`: unique UUID for the event.
- `timestamp`: UTC ISO-8601 timestamp with `Z`; do not accept local-time timestamps.
- `source`: stable repository/service identifier, not a user-controlled display name.
- `type`: allow-listed event type such as `service.health`, `capability.report`, `test.result`, or `audit.record`.
- `payload`: bounded JSON object; never embed credentials, raw shell commands, or unrestricted filesystem content.
- `provenance.revision`: immutable Git commit SHA when the claim is tied to repository code. Omit a claim if its source revision cannot be identified rather than inventing one.

## 2. Evidence labels

Use the canonical labels:

- `PROPOSED`: design intent, target, or planned behavior; not implemented evidence.
- `SIMULATED`: output generated by a model, stub, fixture, emulator, or synthetic test.
- `DEMONSTRATED`: behavior observed in a reproducible test or controlled demonstration; scope and environment must be recorded.
- `MEASURED`: raw observation from an identified instrument or source with procedure, units, timestamp, and calibration context where relevant.
- `UNVERIFIED`: reported or claimed but not independently substantiated.
- `VALIDATED`: a stated acceptance criterion passed with recorded test/evidence references; validation applies only to that criterion and environment.

Do not silently translate labels. If a consumer cannot represent a source label, it must preserve the original label and show it as unknown/unmapped. A report that a test passed is not automatically proof of production readiness or physical quantum operation.

## 3. Health status

Health values are `HEALTHY`, `DEGRADED`, `UNAVAILABLE`, or `UNKNOWN`.

Every remote health observation should include `observed_at`, `source_revision` if known, and a freshness policy. Missing responses, invalid signatures, schema failures, and stale observations produce `UNKNOWN` or `UNAVAILABLE`, never `HEALTHY`.

## 4. Transport and permissions

- Phase 1: local fixture tests and read-only HTTP JSON.
- Phase 2: authenticated read-only HTTP polling; optional WebSocket only after authentication, authorization, message limits, reconnect behavior, and replay controls are tested.
- No cross-repository command execution through this contract.
- No activation, deployment, rollback, Git push, or hardware-control message in v1.
- Any future write operation requires a new versioned contract, named permission scopes, explicit operator approval, idempotency key, audit record, and tested failure/rollback behavior.

## 5. Provenance and retention

Consumers store the original envelope and source identity. Mirroring must preserve the source event ID and classification; consumers may add a separate local receipt record but must not rewrite the source event. Hash chaining can detect certain modifications but does not by itself make storage immutable or tamper-proof.

## 6. Compatibility

A compatible producer publishes a schema version and tests its payloads. A consumer rejects unsupported major versions and invalid required fields. Additive optional fields may be introduced in a minor revision. Breaking field changes require a new major version.

## 7. Implementation status

This document is a proposed shared contract. Do not claim that the three repositories are connected until contract tests and live read-only integration tests pass.
